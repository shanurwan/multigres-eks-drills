Multigres on Amazon EKS, three zones

Upgrade it, move it, cut it off, fill its disk. Watch what the app saw.

Six short lessons on day-2 operations for Multigres, the Postgres sharding and high-availability layer. You type each command. The terminal answers with the timeline of a real run on a three-zone EKS cluster under load, and the picture plays back the cluster second by second: where the primary was, which zone was cut off, what the cluster reported, and how many writes succeeded.

    What the recorded runs showed

    Every number below is computed in your browser from the same records the lab replays. A range is the spread across runs of the same operation.

    Nothing acknowledged was lost

    Across every run, and on both sides of a network partition, each write the database said was committed was still there afterwards.

    "Healthy" is not "can take writes"

    With the primary's disk full, every write failed for 206 seconds while the Shard reported Healthy for most of them. Alert on free space, not only on the phase.

    Planned moves are invisible, gateway restarts are not

    Switchovers held and replayed queries with no app errors. Replacing the gateways closed every app connection once.

    Run it more than once

    Two identical node group upgrades gave 6,288 and 158 app errors. One run tells you what can happen, not how often.

    How it is measured

    Two kinds of load

    supafirehose, Multigres's own load tool, holds 500 app connections through the gateways: 2,000 reads and 200 writes a second, reconnecting on any error. A second tool writes 400 rows a second and records every attempt, so each acknowledged write can be looked up afterwards.

    One clock, started at the operation

    The load runs for a minute first. Every time is counted from the moment the operation starts. The Shard's phase and pod readiness are read every few seconds, and the disk every 10 to 40 seconds.

    What the picture adds

    The dots are a sample drawn from the per-second counts, and the gateway a dot passes through is picked at random. The primary is drawn moving when writes came back, the first moment the record shows clients reaching it.

    What this lab cannot tell you

    One small node per zone, one shard, a free-plan AWS account, one to four runs per operation. The numbers describe this cluster on 27 November 2026. Run it on yours before you believe any of them about yours.

    Run it yourself

    The same Terraform and scripts that recorded these runs, on your own AWS account. About an afternoon, and about USD 0.50 of credit an hour while the cluster exists.

    1. An AWS account and the tools

      A free-plan account is enough. Create a user for Terraform with its own CLI profile, and install Terraform, the AWS CLI v2, kubectl and Git (Git Bash on Windows). Step-by-step guide, with checks.

    2. Fill in the template

      git clone https://github.com/shanurwan/multigres-eks-drills
cd multigres-eks-drills
cp terraform/terraform.tfvars.example terraform/terraform.tfvars

# terraform/terraform.tfvars
region      = "ap-southeast-2"      # any region with 3 zones
profile     = "multigres-lab"       # your CLI profile
owner       = "your-name"
alert_email = "you@example.com"     # the budget alarm writes here
admin_cidrs = ["203.0.113.10/32"]   # your public IP, for the EKS API
budget_usd  = 40

      The file is ignored by Git, so your email and IP stay on your machine.

    3. Create the cluster (about 20 minutes)

      export AWS_PROFILE=multigres-lab AWS_REGION=ap-southeast-2
terraform -chdir=terraform init
terraform -chdir=terraform apply
aws eks update-kubeconfig --name multigres-lab --region $AWS_REGION
kubectl get nodes -L topology.k8s.aws/zone-id      # three nodes, three zones

      It builds a VPC across three zones, EKS with one node group per zone, the EBS CSI driver, an S3 bucket for backups with an IAM role for it, and a budget alarm.

    4. Install Multigres (about 6 minutes)

      kubectl apply --server-side -f https://github.com/multigres/multigres-operator/releases/download/current/install.yaml
failure-drill/scripts/deploy.sh          # the 3-zone MultigresCluster, waits for Healthy
failure-drill/scripts/primary.sh         # which zone holds the primary

    5. Start the load

      cd production-scenario
scripts/build.sh                         # supafirehose and the write checker
scripts/setup.sh <zone-id>               # the load pod
../failure-drill/scripts/writer.sh <another zone-id>
cd ../day2-operations

    6. Run the lessons for real

      export CONNS=500
WRITE_FOR=4m  scripts/day2.sh switchover 1
WRITE_FOR=8m  scripts/day2.sh az-partition 1
WRITE_FOR=12m scripts/day2.sh ng-upgrade 1
WRITE_FOR=12m FILL_LEAVE_MB=1 GROW_TO=20Gi scripts/day2.sh disk-full 1
WRITE_FOR=25m MG_IMAGE=ghcr.io/multigres/multigres@sha256:... \
  PGCTLD_IMAGE=ghcr.io/multigres/pgctld@sha256:... \
  MULTIADMIN_WEB_IMAGE=ghcr.io/multigres/multiadmin-web@sha256:... scripts/day2.sh mg-upgrade 1

      Wait for the shard to be Healthy between runs. Each run lands in day2-operations/results/.

    7. Replay your own runs here

      python3 ../production-scenario/analysis/collect.py results
python3 analysis/day2.py
python3 ../lab/build.py results -o my-runs.json

      Then load the file. It is read in this tab and goes nowhere else.

    8. Tear it down, every time

      kubectl -n multigres-demo delete multigrescluster demo --wait=true   # deletes its volumes
aws s3 rm "s3://$(terraform -chdir=terraform output -raw backup_bucket)" --recursive
terraform -chdir=terraform destroy
aws ec2 describe-volumes --filters Name=tag:Project,Values=multigres-lab   # should be empty
